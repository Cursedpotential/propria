### OPEN — owner decision: how a local upload reaches DuckDB

DuckDB runs inside PostgreSQL. `duckDBSourceURL` accepts only `r2://`, `s3://`, `https://`; its comment: "upload:// and retained worker-local file:// references fail closed; callers must first retain the source at a shared object-store locator." Nothing does that retention, and the real UI's "Choose local file" produces `upload://`. So no locally uploaded file can take the DuckDB path today.

- **A (default)** mount the sealed upload directory read-only into the PostgreSQL container and map `upload://<sha>` to that file for DuckDB. Database, worker and uploads are already on the same host (ovh-files), so this is not the cross-host shortcut D-132 rejected. No extra copy, no R2/B2. Cost: one `agentos-db` redeploy (bounces the live DB) + a small mapping change.
- **B** retain each upload to object storage and hand DuckDB that locator (what the code comment and D-149 tier 2 "`nexus` = upload staging" describe). Adds a stored copy and new writes to R2 while R2 is being retired; B2 was off limits today.
- **C** uploads bypass DuckDB and use the registered Go/SBV decoder. Conflicts with D-149 rule 9 ("DuckDB owns every signature it can process").
