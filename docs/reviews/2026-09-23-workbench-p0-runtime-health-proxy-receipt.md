## Checkpoint

The running Workbench is **unhealthy because its R2 credential is not entitled to the buckets that the Workbench still uses**. The health command requests `GET /health` inside the container and exits successfully only when `status == "ok"` and `object_store is True`. At 2026-09-23 12:19 UTC it had 228 consecutive exit-1 failures. The endpoint returned `status=degraded`, `lancedb=True`, `object_store=False`. Logs identify `HeadBucket(casebible-sorted)` as HTTP 403. Independent read-only SDK probes returned `NotEntitled` for listing both `casebible-sorted` and `nexus`, and HTTP 403 for heading either bucket. The configured B2 vault, in contrast, passed both list and head probes. No object names, credential values, or credential documents were read into this receipt.

The current `SOURCE_ROOTS_JSON` selects B2 `salem-data/consignatio/vault/v1/` as the first/default browser source, followed by the whole B2 bucket. The three R2 source roots are marked temporary. `OBJECT_STORES_JSON` maps the `b2` and `r2` schemes to runtime-mounted credential file paths; `CASEBIBLE_R2_CONFIG_PATH` is a legacy R2 fallback. The present Workbench implementation nevertheless fixes local upload staging to R2 `nexus` under `workbench/staging/`, and its staged-acquisition reference is `r2://nexus/...`. Consequently, passing B2 source browsing does not make staging healthy. The current health check's R2 failure reflects a real unavailable feature; bypassing it would conceal that failure. The older D-149 wording calls R2 Sorted the vault, while the deployed source-root configuration and 2026-09-20 bulk-intake record use B2 as the current vault. This receipt does not decide whether the temporary R2 source roots should be retired.

## Proxy-trust result

The Workbench host port is bound only to `127.0.0.1:18080`. Tailscale Serve forwards the private Workbench service there, with app capabilities accepted. The container observes the host-side socket peer as `192.168.112.1`, and the live exact Serve-peer allowlist is `192.168.112.1/32`. The tailnet auth path is enabled. The device-capability selector in the Workbench environment is empty, so a tagged server-side probe without a Tailscale user identity cannot use its device capability. The auth middleware then falls through to the Traefik check and emits `403 {"detail":"Untrusted proxy"}`. This is the expected denial for that no-identity probe; it does not prove that an enrolled human's Tailscale-User-Login header succeeds or fails.

There is a **separate public-route proxy configuration defect**. The live `TRUSTED_AUTH_PROXY_CIDRS=192.168.112.2/32` names the Workbench container's own address on the shared `probata` network. The `coolify-proxy` address there is `192.168.112.7`; on the application network selected by `traefik.docker.network`, its address is `192.168.48.2` and Workbench's is `192.168.48.3`. Therefore an Authentik-approved public request is expected to be rejected at the Workbench peer check. This conclusion follows the observed network addresses and routing label; it still needs an authenticated public request to prove the actual socket peer and outcome. The correction must use the exact observed Traefik peer after confirming the network selected at deployment, never a broad Docker subnet.

Without identity, the loopback-bound `/`, `/docs`, `/openapi.json`, and `/api/health/deps` each returned 403. Unauthenticated public `/`, `/docs`, `/openapi.json`, and `/api/health/deps` each returned 302 to the Authentik sign-in path. No authenticated public or enrolled-user private round trip was performed. The exact Serve peer is the Docker host bridge address, so these checks do not establish that a host-local process cannot claim the same peer and supply a forged identity header; that boundary needs separate host-level review before claiming protection against a compromised host process.
