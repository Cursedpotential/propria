# HANDOFF — Legal OS Category 3: Chat / AI Agent Orchestration — Implementation Research

Status: rough feature set agreed with owner (2026-08-17); this handoff requests in-depth research to scaffold the actual implementation. Research only — no code, no agent activation.

## Context

Legal OS is a single-user, single-case, self-represented-litigant practice-management app, sibling package to "Agno MCP Platform" in one monorepo. Agno already runs a real agent topology (Root Router → Platform Ops team: ingestion_orchestrator, analysis_orchestrator, review_gatekeeper, transcript_miner; Builder team: dev_copilot, project_pal) on an Agno-framework/AgentOS runtime, with a documented in-flight migration toward "framework-neutral platform API" (their README explicitly lists AG2 as "a bounded coordination candidate, not the approved replacement" — i.e., they are actively evaluating alternatives to Agno-the-framework, not settled). This category is Legal OS's own agent layer: the "Paralegal" conversational assistant plus the "AI Legal Team" (motion/strategy/discovery drafting), which now lives in Legal OS per an earlier owner decision, not in Agno.

## Feature set agreed (do not re-litigate — build research around this)

1. **Global, context-aware summon.** The assistant is reachable via a global shortcut (F1) from *any* panel in Legal OS, not only a dedicated CHAT screen — invoking it pins it into split view (Category 2's split-view feature) alongside whatever panel was already open.
2. **Automatic context injection.** Whatever panel/document/case item is on screen when the assistant is summoned is passed into its context automatically — the owner should never have to re-explain what they're looking at.
3. **Router-first architecture with individually addressable specialists.** Default interaction is through one conversational surface backed by a router/dispatcher (matching Agno's own "Root Router (route mode)" pattern) that determines which specialist agent should handle a given ask. Individual specialist agents remain **directly addressable** too, via the existing mnemonic command bar (Category 2) — e.g., a power-user who knows they want the motion drafter specifically should be able to jump straight there, bypassing the router, the same way `PREC`/`CTRX`/`BRF` already jump straight to their panels.
4. **Grounded in Agno's promoted facts, not raw claims.** Per the Category 1 decision, agent responses that cite case evidence should be grounded in SurrealDB's established facts / promoted evidence subgraphs once that surface is production-ready, with Agno's plain REST API (`/v1/matters/*`, `/v1/knowledge/items`) as the interim/fallback grounding source.
5. **Scope for v1: action-capable, not just advisory (owner decision, 2026-08-17).** The assistant should be able to act from chat — queue a document for analysis, fill in or run a workflow step, etc. — not just research and advise. Given the stakes of legal case work, and matching Agno's own established pattern (their `apply_db_modification` tool is gated behind a native `@approval` / `requires_confirmation=True` HITL flow before any write executes), **default recommendation is to gate consequential actions behind an explicit confirm step** (e.g. "Queue `vendor_nda.docx` for analysis? [Confirm]") rather than silent auto-execution — lower-stakes/reversible actions (like queuing analysis) could have a lighter-touch confirmation than higher-stakes ones (submitting a workflow that emails something, or anything touching case-filing content). This tiering is a research question below, not settled yet.
6. **"Deep research" mode, added 2026-08-17.** Beyond single-shot retrieval, the assistant should support a multi-hop research mode: decompose a research question, issue multiple searches against Category 4's search tools (across whichever sources are configured — case law, statutes, general web, the internal knowledge base), read/evaluate results, refine and re-query, and synthesize a final answer with citations — rather than one search call per question. This is an orchestration-layer capability built on top of Category 4's tools, not a Category 4 feature itself; Category 4 only needs to expose clean, well-typed search functions this mode can call repeatedly.
7. **AI Legal Team personas still need to be authored.** Confirmed via direct repo inspection: Agno's own `knowledge/legal/` directory contains only two coercive-control forensic classification files — no Gemini Gems persona ports, no motion/strategy/discovery agent instructions exist anywhere yet in either repo. This is greenfield content work, not a port of existing code.

## Research questions to answer (with citations/links)

1. **Agent orchestration framework for Legal OS's own agent layer.** Candidates to evaluate: (a) the same Agno framework Agno Platform currently runs (consistency, but note Agno's own docs already flag it as being migrated away from — is adopting it in Legal OS now sensible, or premature?), (b) AG2 (the candidate Agno itself is evaluating — same caveat), (c) LangGraph, (d) a lighter hand-rolled router + tool-calling loop with no framework at all, given this is a single-user app, not a multi-tenant platform. Also evaluate where **DSPy** (owner already uses this for prompt optimization elsewhere) and **LlamaIndex** (owner already uses this) fit — likely not as the orchestration framework itself, but as components (DSPy for optimizing the router's classification prompt and specialist instructions; LlamaIndex for retrieval over the knowledge base). Give a clear recommendation with tradeoffs, not a survey.
2. **Router/dispatcher implementation pattern.** Study Agno's actual Root Router implementation (in their `server/agents/` — check `factory.py` and whichever module wires the router) for a concrete pattern to adapt, rather than designing from scratch. Compare rule-based/keyword routing (fast, cheap, what legal-terminal's demo fakes) vs. LLM-based intent classification (slower, costs tokens, more flexible) vs. a hybrid (cheap rule-based first pass, LLM fallback for ambiguous asks) — recommend one.
3. **Context-injection mechanism.** Research patterns for passing "current UI state" (active panel type, visible document/case/clause ID, any user selection) into an LLM conversation efficiently — e.g., a structured context object attached to each turn vs. a lightweight RAG-style lookup triggered by the router. Tie this to Category 2's state management choice (Zustand or whatever the framework decision lands on).
4. **Persistent/pinned chat session across navigation.** Once summoned into split view, the chat session must survive the owner navigating the *other* pane to different panels — confirm this is a straightforward state-management concern (session lives in global state, not panel-local state) rather than something needing a dedicated backend session store for v1.
5. **Model routing/cost control.** Agno already runs a Portkey gateway (Ollama Cloud primary, NVIDIA embed/rerank/backup, LiteLLM retired). Research whether Legal OS's agents should route through that same Portkey instance (reuse, one gateway to manage, one place to enforce the Confidential-Mode-routes-to-local-Ollama rule from the Category 2/CONF privacy feature) versus standing up a separate one. Recommend reuse unless there's a concrete reason not to.
6. **AI Legal Team persona/instruction authoring approach.** Since no persona content exists yet anywhere, research how to structure this: (a) study Agno's own `server/agents/instructions.py` pattern for the file/module shape to mirror, (b) assess whether the owner's existing `genesee-family-court-toolkit` Perplexity skill (Genesee County, MI 7th Circuit Family Division procedure) is suitable raw material to seed a "Michigan family law" specialist agent's instructions, and how that content would need to be adapted from a "skill for an AI assistant" format into whatever instruction format the chosen framework expects.
7. **Action-confirmation tiering.** Design (research, don't build) a concrete tiering of which chat-triggered actions execute immediately vs. require an explicit confirm click — survey how comparable agentic tools (e.g. Claude Code / Cursor's own tool-approval UX, or Agno's `@approval` decorator options) expose this distinction, and recommend a concrete list of Legal OS actions sorted into each tier (e.g. "queue for analysis" = low friction, "save/overwrite a draft," "mark evidence reviewed," "trigger a notification/webhook" = confirm required).
8. **Deep-research mode design.** Research established multi-hop agentic research patterns (query decomposition, iterative search-and-refine loops, stopping conditions, citation tracking across hops) and recommend a concrete loop structure compatible with whichever orchestration framework question 1 recommends. Keep this bounded (max hops/cost per research session) given the cost-consciousness already established elsewhere in this project.
9. **Grounding/retrieval tool-calling against SurrealDB.** Once the orchestration framework is chosen, research how a specialist agent would issue a "give me established facts relevant to X" query against Agno's Surreal analytical surface as a callable tool — reference Agno's own `tests/test_surreal_investigation_phase0_contract.py` for the query shape already validated there, rather than inventing a new query pattern.
