# HANDOFF — Legal OS Category 4: Research Tools (Precedent / Statute / Citation) — Implementation Research

Status: rough feature set agreed with owner (2026-08-17); this handoff requests in-depth research to scaffold the actual implementation. Research only — no code, no source integrations activated.

## Context

Legal OS is a single-user, single-case, self-represented-litigant practice-management app for a Michigan family-law (custody) matter. This category covers precedent/case-law search, statute lookup, and citation validation/normalization — the PREC/STAT/CITE panels from the earlier UI catalog, backed by legal-mcp-style tools (`search_precedents`, `search_case_law`, `extract_statute`, `validate_citation`, `normalize_citation`).

## Feature set agreed (do not re-litigate — build research around this)

1. **Configurable, pluggable research sources — this is the core requirement of this category.** The owner explicitly wants to add sources beyond CourtListener without code changes: upload a JSON config file plus an auth token through the app's Settings UI, and the new source becomes usable. Do not hardcode a fixed source list.
2. **Internal canonical data model.** Every research panel (PREC/STAT/CITE) renders against one internal `Case`/`Statute`/`Citation` shape, regardless of which configured source the data came from. Each source's config must include a field-mapping spec that translates its native response into this canonical shape.
3. **Source config format, rough shape (owner's proposal — validate/refine, don't discard):** base URL, auth type (bearer token / API key header / basic) + the token itself (entered separately from the JSON file, never embedded in it), one or more endpoint templates (e.g. a search endpoint, a lookup-by-ID endpoint), and a field-mapping section.
4. **Built-in default sources.** CourtListener/RECAP ships pre-configured as a default source (free, no owner setup beyond an optional API token for higher rate limits). Research and recommend whether Midpage (a legal case-law research tool the owner already has connected in their Perplexity project) should also ship as a second built-in default, or whether it's better suited to the generic add-a-source flow.
5. **Citation parsing via a real library, not hand-rolled regex.** Use [`eyecite`](https://github.com/freelawproject/eyecite) (Free Law Project's own open-source citation extraction/normalization library — the same one powering CourtListener) for the Citation Console's validate/normalize logic, rather than reimplementing citation-format detection from scratch.
6. **Scope: no fixed "search all of law" requirement.** This can legitimately be scoped to Michigan family/custody law content plus whatever sources the owner configures — it does not need to compete with a general legal-research engine.
7. **Search architecture gap-fix, added 2026-08-17 (do not skip this section).** The original discussion for this category covered *sources* (CourtListener, Midpage, pluggable custom sources) but never actually specified the *retrieval mechanism* used to search across them plus Legal OS's own internal knowledge/documents. Four things need to be covered that were missed the first pass:
   - **Hybrid search (dense vector + sparse/BM25 retrieval)** over the internal knowledge base and document workspace — this is squarely the owner's own area of professional expertise (they've implemented this exact pattern before), so this should be a genuinely well-executed piece, not an afterthought. Research current best-practice hybrid retrieval approaches (e.g. reciprocal rank fusion combining a vector index with a BM25/full-text index) and recommend a concrete implementation given the stack already in play (Postgres with `pgvector` is already available per Category 1; confirm whether Postgres full-text search (`tsvector`) alongside `pgvector` is sufficient for hybrid search in-database, versus needing a dedicated search engine).
   - **Full-text search** over the owner's own documents (Category 5's workspace) and saved research — likely the lexical half of the hybrid-search pair above, not a separate system.
   - **General web search** (secondary sources, practice guides, legal news — not structured case-law APIs) — recommend this be implemented as just another configured source in the pluggable-source framework (question 1 above), using a general web/search API (e.g. Brave Search API, or the owner's existing Perplexity access) rather than building a separate web-search subsystem.
   - **Note:** an agentic "deep research" mode (multi-hop, multi-source synthesis) is explicitly NOT part of this category — it belongs to Category 3 (chat/agent orchestration) as a capability that *calls* this category's search tools repeatedly. Do not scaffold multi-hop research logic here; just make sure the search tools this category produces are callable cleanly by that future orchestration layer (a clean, well-typed search function signature, not a UI-coupled one).

8. **Content retargeting from the legal-mcp/legal-terminal baseline:** statute quick-links should point at the Michigan Child Custody Act / MCL 722.23 best-interest factors and other Friend-of-the-Court-relevant statutes instead of generic examples; precedent search examples should be family-law-oriented.

## Research questions to answer (with citations/links)

1. **Declarative connector format — build from scratch or adapt an existing pattern?** Evaluate [Airbyte's low-code Connector Builder](https://docs.airbyte.com/connector-development/config-based/low-code-cdk-overview) (a JSON/YAML manifest describing a REST API source: auth, pagination, endpoints, field extraction) as the closest real precedent for exactly this use case. Recommend either adopting a subset of that pattern directly, using a lighter existing library, or a justified from-scratch minimal schema — with a concrete example schema for a CourtListener-equivalent source as the worked example.
2. **Secure storage for user-supplied API tokens.** Given the app runs on the owner's own VPS (per Category 1's Postgres-schema persistence decision), research whether tokens should be encrypted at rest in Postgres (e.g. `pgcrypto`) with the encryption key held outside the database (env var), vs. a separate local secrets file with restricted file permissions, vs. reusing whatever secret-handling pattern Agno's own platform already uses for its CourtListener/PACER credentials (`integrations/config.py` in legal-mcp is the closest reference pattern — check whether Agno platform has its own more mature convention worth matching instead, given the monorepo).
3. **JSON config validation.** Recommend a validation approach (e.g. Python's `jsonschema` library against a meta-schema Legal OS defines for "what a valid source config looks like") so a malformed uploaded config fails cleanly at upload time rather than breaking search at query time.
4. **Field-mapping expression language.** For translating an arbitrary source's JSON response into the canonical `Case`/`Statute`/`Citation` model, evaluate simple JSONPath-style mapping (e.g. via the `jsonpath-ng` library) vs. a more constrained key-remapping-only approach (less powerful, harder to misconfigure, likely sufficient for REST JSON APIs). Recommend one, with the tradeoff stated.
5. **`eyecite` integration specifics.** Confirm current version/maintenance status, and sketch how its output (parsed citation objects with reporter/volume/page/court/year) maps onto the existing Citation Console's `validate`/`normalize` tabs from the earlier UI catalog.
6. **Midpage evaluation.** Research what Midpage actually offers (API availability, auth model, content coverage of Michigan family law) to determine whether it's a good candidate for a second built-in default source, and if so, produce a worked example of its source config in the format from question 1.
7. **Hybrid retrieval implementation.** Given `pgvector` and Postgres full-text search are both already available in the shared Postgres instance (Category 1), research whether an in-database hybrid approach (vector similarity + `tsvector`/BM25-style ranking, combined via reciprocal rank fusion) is sufficient, or whether a dedicated search layer (e.g. Weaviate, which Agno already runs) should be reused instead for consistency with Agno's own retrieval stack. Recommend one, citing current best-practice hybrid-search fusion techniques.
8. **Rate limiting / cost awareness per source.** Some sources (paid legal databases) could incur real costs per query the way PACER does for Agno. Research a lightweight pattern for a per-source "this may cost money" flag and/or a query budget/warning, mirroring the PACER fee-warning pattern already established in the UI catalog.
