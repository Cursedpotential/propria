# Advocatio — reconciled direction and deliverables

Advocatio becomes the legal-work module of one unified Propria surface: dense, readable, mouse-and-keyboard friendly, with a simpler phone/reference view of the same underlying records. It combines the complete Family Court Toolkit, shared legal references and methods, source-linked case work, document creation/review, timelines, and the multidisciplinary digital firm. Full convergence is staged; existing remote tools and stores can provide useful bridges along the way.

## The information model

The three main collections are **legal material**, **methods and skills**, and **private case context/work product**. They remain linked without being collapsed into one kind of record. A drafting skill provides a method; reference sources provide the law/material; accepted case sources support factual statements. Each source, method, analysis and document keeps an identifiable version.

The current Michigan toolkit is the baseline to reconcile in full. First check its existing remote database and MCP migration: preserve what already works, compare local and remote manifests, and import only what is missing or needs a new version. Earlier plugin versions and the 113-source batch supply candidates, corrections and reusable ideas. Track each item's disposition so completeness is measurable.

## The working experience

The proposed main areas are Case overview; Timeline; Claims and evidence; Legal references; Documents; Strategy and risks; Hearing preparation; Discovery; Calendar and tasks; Digital firm; and Tools and connections. These are information groups within the common surface, not eleven new isolated applications.

Keep the useful current shell: full page names, clickable actions, keyboard navigation, assistant beside the work, and split/pinned source views. Use ordinary language. Technical IDs, tool payloads and provider details remain available in inspectors. Compact flags show missing support or unfinished review; repeated disclaimer banners are explicitly excluded.

The phone/reference view opens resources, records, calendar and relevant source details using the same identifiers and permissions. It does not need the full analysis/tool layout. Agent reads use the same scoped data contracts.

## Delivery sequence

1. **Recover and prove:** finish toolkit remote/local reconciliation, port/service inventory, donor/skill code coverage and current app baseline. Preserve current working-tree changes.
2. **Make storage and contracts dependable:** atomic revisions, source identity and access, common client/auth slice. This precedes broad case-content import.
3. **Deliver useful reference/tool access:** shared collection and method help, generic MCP registration/discovery/manual calls, first Toolkit and CourtListener reads. Existing remote capability can be used before full port.
4. **Connect claims and timelines:** source support, gap reports, retained visualization engines and Timesketch curation adapter/common-surface slice.
5. **Build review-centered documents and strategy:** court-language proposals, revision decisions, four checks, private context/risks/analysis follow-up.
6. **Complete court work and firm workflows:** office/forms/derivatives, hearing/discovery outputs and recovered firm protocol.
7. **Converge remaining integrations:** language/module ports, saved/report/monitoring workflows, common desktop/phone behavior and verified service cutovers.

## What the audit changes in the plan

- The current timeline is another docket view; relationship/claim chronology and the existing Timesketch fork must be integrated explicitly.
- Current citation presence is credited too broadly as support. Claim-level support and four independent review results are core work, not optional polish.
- Current ordinary revisions and aggregate-save behavior need attention before importing substantial personal material.
- Original office requirements are larger than the current text editor. LibreOffice and interactive office work were held, not discarded.
- Stack unification was decided; current Next is migration source. The exact package baseline and donor language transitions need recorded implementation dispositions.
- Outside projects were not all just mood-board inspiration. The handoffs establish a real fork and retained integrations; other candidates remain traceable pending decisions.
- Existing remote toolkit/database work may reduce what needs to be moved. Connected session console tools work, but they are a subset of the full plugin.
