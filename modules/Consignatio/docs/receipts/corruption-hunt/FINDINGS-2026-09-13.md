# Corruption hunt: zero-filled payloads in R2 and B2

> _Byline: Claude Code · Opus 5 · 2026-09-13_

This hunt was read-only. Nothing was copied, moved, renamed or deleted. Object bytes were read only for the 6 tiny B2 files and 2 test documents named below.

## Method
- **Zero-fill fingerprint:** for every object size present, compute the MD5 (R2) or SHA-1 (B2) of an all-zero payload of that size. Match it against the inventory hashes. A file that was never really downloaded but was saved anyway often keeps its full size and contains only zeros.
- **R2 source:** `casebible/casebible.duckdb` → `r2_files`, 1,279,556 rows. The same data is in hosted PG on ovh-files: container `fgz1n7useplhk0t91uk7k1aw`, database `casebible`, schema `raw_duck`.
- **B2 source:** a fresh `rclone lsf b2:salem-data -R` listing: 103,076 objects, 262.04 GB. 117 objects have no SHA-1; all are 0.21–78 GB.
- **OneDrive source:** `casebible/od_case_bible.tsv`, 211,720 rows of size and path.

## Root cause lead: D:\Backup (verified by local byte read)
- **`D:\Backup` holds zero-filled copies:** `Chrome Passwords.csv`, `Chrome Passwords 3.csv`, `location-history 2.json` and `location-history 4.json` are all zeros.
- **Their MD5s equal the zero-filled Google Drive `99_Archive/Documents` copies** (`fb4055…`, `d9a5c9…`, `fe66e4…`, `238afa…`).
- **So the zero-filled bytes spread from `D:\Backup`** to Google Drive `99_Archive` and to the R2/B2 `_backup_import` tree (the local `_backup_import` source is 852,205 files / 608.8 GB).
- **`D:\Backup/Matthew-Salem.pdf` is real.**
- **Full local zero-fill scans of `D:\Backup`, F: and J: are running.** Outputs go to `dbackup/`.

## Quarantine applied (owner-approved 2026-09-13, one step at a time)
Owner decisions:
- Flag and exclude in the catalogs, keeping every row.
- Null the hash on zero-filled rows; zero-byte files carry no hash.
- A zero-filled file must never match a good file.
- Nothing is deleted.

Before any move, a Chesterton's-fence review checked what each move could break. It found two hazards:
- The paused `casebible-raw.files-from-raw` transfer list held all 6,362 zero-filled keys, so a resume would have copied them back.
- Google Drive for Desktop backs up "My PC" folders, so local quarantine folders must stay inside each backup root.

> **Known defect in `dbackup/F_all_zero.tsv` (and `J_all_zero.tsv`):** the first `zero_scan.py` run was given a bare drive root. `os.walk("F:")` returned `F:case\…` with no separator, so every relative path in those files **lost its first character** (`ase/…` is really `case/…`, and `isk Drill/…` is really `Disk Drill/…`). `zero_scan.py` has since been fixed. `local_zero_quarantine.py` repairs a row only when exactly one top-level entry fits, and the repaired file must still pass the exists, same-size, all-zero and no-overwrite checks. D:\Backup paths are correct.
