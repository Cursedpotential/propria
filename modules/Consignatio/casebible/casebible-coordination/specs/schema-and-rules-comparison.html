1 · THE TABLES — where a message lives

Current: analysis.normalized_record

CREATE TABLE analysis.normalized_record (   -- CURRENT ingest target (populated)
  id UUID PK, artifact_id -> evidence.evidence_hash,
  record_type  message|call|event|media,
  source TEXT,                      -- parser key ('imessage-html')
  conversation_id TEXT,             -- filename/session-derived, NOT identity
  role TEXT,                        -- 'owner' / raw label — NO real identity
  participants JSONB,               -- display labels, no entity linkage
  content TEXT, occurred_at, knowledge_time, disclosure_tier,
  attrs JSONB                       -- everything else, schemaless
)

What it gives you: provenance to the source file via artifact_id ✓ · bitemporal ✓.
What it can't do: no real-name identity (role is a raw label), no per-message recipient, no multi-party model, conversation_id derived from filenames. Detection currently reads THIS.

Designed master: analysis.message (+ participants)

CREATE TABLE analysis.message (            -- DESIGNED master (0005, applied, EMPTY)
  id UUID PK -> normalized_record(id),
  conversation_id -> analysis.conversation,
  ts_utc, platform, external_id, serial_number,
  prev_message_id / next_message_id,        -- thread ordering
  sender_raw, sender_e164, sender_entity_id -> entity/person,   -- REAL identity
  recipient_raw, recipient_e164, direction in|out,
  content_sha256, word_count, char_count, language,
  raw_ts, tz, temporal_confidence,          -- full temporal provenance
  platform_attrs JSONB, raw_data JSONB
  -- rollup flags: has_behaviors/behavior_count (derived counters, not verdicts)
);
CREATE TABLE analysis.message_participant (  -- MULTI-PARTY (from/to/cc/group/third_party)
  message_id -> message, entity_id, participant_raw, participant_e164,
  role from|to|cc|bcc|group|third_party, conduct_party
)

Your requirement, already designed: provenance ✓ (chains to normalized_record → evidence_hash → evidence.source), real identity ✓ (sender_e164 + entity/person link), recipient ✓, direction ✓, multi-party ✓ (message_participant incl. third_party), thread ordering ✓, per-message content hash ✓.

Verdict: the "master table with no analysis, full provenance, real names, more than two people" already exists in the applied 0005 schema — it is just EMPTY. Ingestion stops at normalized_record. The work is a population step (normalized_record → message + message_participant + entity resolution), not a new design.
One purity note to decide: message carries derived rollups (has_behaviors, behavior_count, max_behavior_severity, *_hint columns). They're counters/hints, not verdicts — but if you want the master table 100% analysis-free, we strip them into a side table. Annotate here with your call.
