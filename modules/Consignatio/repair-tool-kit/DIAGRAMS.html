6 · Conversation ingestion — XML and JSON

DuckDB is the query engine, but it cannot be pointed at the raw file. Two limits force a pre-pass.

flowchart TB
  A["source.xml
3,852,198 B"] --> B["slim pass · lxml"]
  B --> C["blobs/<sha256>
8 files · 2,822,412 B"]
  B --> D["slim.xml
89,925 B"]
  B -.-> N["set data_sha256 on
ALL parts, even empty"]
  D --> E["DuckDB read_xml"]
  E --> F["messages · 231"]
  E --> G["mms_parts · 14"]
  E --> H["mms_addrs · 12"]
  F & G & H --> I["Parquet"]
S-1 · Sparse attributes vanish. Only 8 of 14 parts had data=. DuckDB's sample-based inference omitted the field entirely and every image disappeared with no warning. sample_size=-1 does not help. Setting the attribute on every element does.
S-3 · XPath functions OOM. xml_extract_attributes(xml,'//sms') consumed 3.1 GiB on a 3.8 MB file. Never use them for bulk work.

JSON — same two-stage shape, different hazards

Facebook and Instagram exports take the identical pattern: normalize first, then DuckDB. Both paths emit the same tables, so SMS and Facebook threads land in one corpus.

Phase 5b gotchas are marked [expected], not [observed] — documented exporter behaviour, not yet reproduced against Matt's own files.
S-8 · Meta double-encodes everything. [observed] UTF-8 bytes written as latin-1 then escaped, so Rados\u00c5\u0082aw parses as valid JSON with no error and yields Ã©-style mojibake. Unfixed since 2018; no export setting, no alternative parser. Fix at byte level before json.loads; post-parse latin-1 works today but breaks on mixed content. ftfy runs after as a detector — any further change means something else is wrong.
S-14 · The most-cited fix eats emoji. [observed] The popular Stack Overflow answer pairs \u00xx sequences two at a time. Accented Latin is exactly two, so it looks correct — then 💎 → П and ❤️ → ¤ϸ, silently. Emoji are four to six sequences. Consume runs of arbitrary length.
A-10 · No direction field. Meta exports have no type or msg_box. Direction is derived by comparing sender_name to the account owner — a display name that can change or collide. Tag it confidence:"derived", never "structured".

6b · ZIP — container, not leaf

Most evidence arrives zipped. Unwrapping and routing the contents is the common case; repair is the fallback. This is what makes the pipeline recursive.

flowchart TB
  Z["archive.zip"] --> C1["channel 1
archive/zip
central directory"]
  Z --> C2["channel 2
scan PK\x03\x04
local headers"]
  C1 & C2 --> CMP{"counts
agree?"}
  CMP -->|yes| G["safety gate"]
  CMP -->|no| F["record FINDING
both counts kept"] --> G
  G -->|"path escape"| X["REFUSE
+ record"]
  G -->|"ratio / depth cap"| X
  G -->|ok| M["members → blobs/<sha256>"]
  M --> P["profile + route each member"]
  P -->|"member is a zip"| Z
  Z -.->|"damaged"| R["repair ladder
zip -FF → ziptail → bsdtar → 7z → carve"]
  R --> C1
Go's archive/zip never reads local headers, so channel 2 is the only way to see an entry the central directory omits.
S-10 · Zip slip. A member may be named ../../../Windows/System32/x.dll. Go hands you the name verbatim and does not validate it. Refuse and record — never sanitize and continue. A malicious name is a finding.
S-11 · Bombs compound under recursion. Three caps — total bytes, per-member ratio, depth (default 3) — tracked cumulatively across the whole recursion, not per archive.

6c · Every derived value shows its work

A bare confidence label tells a reader nothing they can check. Anything not read directly from a structured field carries its own justification, traceable to bytes in the original.

flowchart LR
  V["derived value"] --> L["level

  V --> W["why

  V --> D["derived_from
element IDs + byte offsets"]
  V --> M["method

  V --> A["assumptions

  V --> N["not_established

not_established is load-bearing and the field most likely to be skipped. It is what stops a derived value being read as a stronger claim than it is.
levelmeans
structuredread from a labelled field the exporter wrote — SMS type, addr type
derivedcomputed from structured fields — Meta direction from sender_name
header_derivedread from printed text laid out for humans — PDF transcript headers
ocr_derivedrecognized from pixels

R11. A PDF header is not a type code and is never recorded as one. Flags follow the same discipline — whatever raised a flag states why it raised it, or it is noise.

Two views of every payload. blobs/ is content-addressed and correct for integrity. attachments/ is the same bytes under real filenames so the package can actually be opened and looked at. A folder of 64-character hashes is not reviewable.
S-13 · Declared type lies. [observed] The reference export declares ct="image/png" on parts whose bytes are JPEG, with cl filenames that match neither. Identify by magic bytes, store declared_type and detected_type as two fields, and treat disagreement as a finding rather than something to fix quietly.
R6. Originals are never opened for write. A correction never edits a package — it creates a successor naming its predecessor.

9b · Corpus index and corroboration

Packages are the source of truth. The index is a view over them — derived, disposable, and rebuildable byte-for-byte at any time.

A disagreement between two sources is a finding, surfaced and never auto-resolved. Confidence is never flattened — a header_derived row stays distinguishable from a structured one in every query.

Three states, and accepted is what stops this becoming an infinite to-do list. Nothing is deleted — a gap is closed with a stated reason.
A-16 · Ranking order is not the obvious one. A screenshot's EXIF timestamp records when the screenshot was taken, not when the message was sent — routinely months apart. So OCR keyword match is the primary signal and time proximity is a tiebreak. A candidate whose timestamp is far from the message is the expected case, not a disqualifier.
Keywords are chosen by rarity, not by eye. Terms rank by inverse frequency across the corpus. ok and laundry are worthless; Miralax, Clio high school, famous footwear discriminate. Each term's corpus frequency is recorded with the match, so a hit on a once-in-40,000 term reads as a stronger claim than a hit on a common one — rather than both just saying "matched".
Why this matters more than it looks. A PDF-derived message with an independent screenshot at the same timestamp is a stronger record than an uncorroborated one from the same PDF. Coverage turns "I have enough screenshots across the span" from an assertion into something measurable — and shows where the gaps still are while they can be filled.

Subprocess engines, JSON contractlockedno language lock-in; the winning reader was not predictable
Extract always, repair on requestlockedextraction is non-destructive, so it needs no justification
Profile → route → one engine → checklockedconsensus on every file does not pay for itself
DuckDB + slim pre-pass for XMLlockedverified on the real export; neither half works alone
Same pattern + same tables for JSONlockedMeta exports have the same sparse-key hazard; shared shape puts SMS and Facebook in one corpus
ZIP as container-first, repair-secondlockedmost evidence arrives zipped; unwrap is the common case, repair the exception
