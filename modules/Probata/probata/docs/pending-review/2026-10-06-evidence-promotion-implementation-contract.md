That supersedes the historical D-152 instruction to defer building promotion. It does not supply a real item, approve any promotion, or make the old producer safe to enable.

The canonical destination is `evidence.evidence_item`. The schema snapshot calls it the promotion target and says it is written only through a `canon.change_proposal` of kind `promote` after an owner ruling (`modules/Probata/probata/sql/bootstrap/schema_snapshot_20260907.sql:7031-7048,7089`). The current `server/case_management/repository.py::promote_evidence` is not this workflow: it writes `analysis.evidence_item` and `analysis.knowledge_evidence_promotion` (`:822-901`), while `server/case_management/service.py::_require_advanced_evidence` fails closed and `repository.get_case_management_capabilities` reports `advanced_evidence_available=False` (`service.py:44-47`, `repository.py:114`). ## Required request and provenance shape

Use one promotion item per `canon.change_proposal`, even when the UI submits a batch. The request must identify an authoritative PostgreSQL `context.source_version` and its retained original-object identity; it must not accept bytes, arbitrary filesystem paths, callback URLs, or a caller-selected object-store URL. For the direct path, the source-version ID is the selection. For the analysis-origin path, carry the Surreal record/analysis reference as origin provenance, then resolve and verify its mapping to that same authoritative source-version/original pair before filing the proposal. Surreal remains an analysis surface and is never a second evidence writer.

The current retained-source read seam is `modules/engine/postgres/hash_repository.go::Repository.OpenOriginal`: it accepts an `original` reference, resolves it through `context.retained_object`, and opens inline bytes or the configured object opener (`:54-74`). The object-store path is `modules/engine/acquisition/objectstorage.go::ObjectStoreResolvers` / `NewObjectStoreResolver` (`:97-135`); `objectStorageVersion` rejects malformed, duplicate, empty, `null`, or oversized `versionId` values (`:221-237`). The current `SourceIntegrityStore.OpenSourceIntegrity` resolves a pinned workflow request and calls `OpenOriginal` (`modules/engine/postgres/source_integrity_store.go:111-117`). These are source-reading siblings, not a promotion workflow or custody hash writer. The source-integrity activity is a bounded byte assessment (`modules/engine/activities/source_integrity.go::AssessSourceIntegrity`, `:85-90`), and its store persists activity execution/receipt state; it does not establish H1/H2/H3.

Promotion must retain, at minimum, the source-version ID, retained original-object ID, exact immutable object reference/version, independently re-read SHA-256 of the original, and the original/package fingerprint comparison required by D-154. For an analysis-origin item it must additionally retain the opaque Surreal origin reference and the verified source-version mapping. The analysis reference is provenance, not authority to substitute a different source. D-154 requires reopening the retained Intake Source Package and re-reading/rehashing the packaged original; an intake/context fingerprint cannot be relabeled as custody (`DECISION_LOG.md:345`).

## Proposal, ruling, and operation lifecycle

The schema supports `canon.change_proposal` kinds including `promote`, per-row `target_pk`, `patch`, `origin_surface`, `origin_ref`, `proposed_by`, `source_generation`, `tier`, and statuses `proposed`, `approved`, `rejected`, `stale_requeued`, `applied`, `failed` (`schema_snapshot_20260907.sql:7477-7493`). `canon.change_decision` records `proposal_id`, `decided_by`, `decision` (`approve`, `reject`, `requeue`), optional batch ID, note, and time (`:7461-7469`). The owner ruling is per item; a batch is presentation/orchestration only and cannot collapse approvals.

`canon.apply_proposal(proposal_id, decision_id)` performs a generation staleness check and says non-`correct` kinds are executed by their kind-specific worker (`schema_snapshot_20260907.sql:1088-1110,1115-1116`). However, the function does not check that `decision_id` belongs to this proposal or has decision `approve`; it also advances the canonical-table generation, inserts a `change_application`, and marks the proposal `applied` even for `promote` (`:1141-1157`). A promotion executor must not call it as though it were an owner-approval validator. The approved execution transaction must bind the proposal and its specific approved decision, reject wrong-proposal/non-approve/replay decisions, enforce `source_generation`, and commit the evidence item plus application receipt atomically (or add a specifically designed, durable kind-worker state that does not falsely call an uncommitted promotion `applied`).

The proposal schema has no request idempotency key or unique `(origin_ref, source)` constraint. The legacy Knowledge route demonstrates an advisory-lock plus existing-ledger pattern (`repository.py:829-836`), but that table is not the universal proposal ledger. The new API/workflow must persist a stable idempotency identity bound to a canonical request digest and source version, serialize concurrent duplicates, return the same durable proposal/operation on identical retry, and reject a changed-payload replay. It must not rely only on an in-memory progress map or Temporal start alone. A proposal-linked workflow ID can be stored in `origin_ref` only if the proposal transaction makes it durable before dispatch and retry recovery handles the commit/dispatch gap.

Expose persistent status from durable proposal/application and workflow/receipt state. Pending approval, stale/requeued, running stage, failed stage, and package-blocked must remain visible. “Evidence committed” requires read-back of the exact `evidence.evidence_item` and its source/hash lineage. “Package complete” is a later status and must not be inferred from a proposal being approved/applied or a workflow returning success.

## Custody, hashing, and package completion

`server/evidence/AGENTS.md` names `server/evidence/custody.py` as the only writer of the `evidence` schema and `ingest_artifact()` as the H1/raw custody gate. In code, `ingest_artifact()` computes H1, deduplicates, writes the write-once blob and H1/source row; its own contract says it does not generate H2/H3 (`custody.py:268-283`). `record_evidence_hash()` appends a supplied hash; `reconcile_sbv_import()` independently checks H1 and records the SBV-specific H2/H3 chain (`:541-643`). That is not a general H2/H3 contract for arbitrary source types. D-152 moved custody hashing to promotion time; D-154 requires exact original reread. Do not reuse the context fingerprint or generalize SBV's record/chain construction to unrelated formats.

The implementation therefore needs an explicit, one-writer design: extend the sanctioned custody writer with a proposal-bound promotion operation, or obtain an explicit owner-approved change to the sole-writer boundary before a separate kind-specific writer is added. The writer must run only after the verified per-item owner decision, and must use source/version-bound idempotency so Temporal retries cannot create a second evidence item or custody chain. H1 is the original-byte hash; H2/H3 must be emitted only where the selected format has a defined canonical record/chain contract. If a source type lacks that contract, the item remains pending/blocked with H1 and source provenance intact; it is not marked package-complete.

`server/contracts/legal_source_package.py::LegalSourceItem` requires exact evidence and assertion versions, source version/locator/content hash, a source-verification receipt ID, and a human-authorization receipt ID (`:92-122`). `assemble_package()` requires issuer/key ID and committed items (`:243-273`); its module header explicitly says no production issuer or route is wired while D-152 holds (`:1-5`). A package may be reported complete only after: (1) source reread and hash/version comparison succeeds; (2) the human authorization is recorded by the actual authorized principal; (3) the approved proposal and exact evidence row/hash lineage commit and read back; (4) assertion/version references and both required receipt IDs resolve; (5) the configured trusted issuer signs the package; and (6) package verification/current-status and the required delivery/read-back path succeed. No receipt or issuer identity may be fabricated to pass these gates.

## Smallest safe implementation seam

1. Add a strict promotion request/status contract and case-management route. Resolve direct and Surreal-origin selections server-side to the same retained original/source-version identity. Reject unresolved analysis references, unpinned or mutable source references, AI-chat/context-only sources, and caller-supplied bytes/paths/URLs.
2. Persist one idempotent `promote` proposal per item with origin provenance, request digest, source version, and current canonical generation. Add an owner decision endpoint that binds the authenticated owner principal to `decided_by`; keep proposal creation separate from ruling. Do not auto-adopt `evidence_item`.
3. Register a new durable Temporal promotion workflow with separate source-reread/hash, supported record-hash, proposal-bound evidence commit/read-back, and package-assembly/verification activities. Reuse the existing retained-original resolver and issuer/package contract; do not turn `AssessSourceIntegrity` into a hasher or enable the legacy writer.
4. Complete a proposal-specific transactional executor in the sanctioned evidence writer. It must validate the exact approved decision, perform idempotent custody/evidence writes, honor the canonical generation, and only then transition durable status to committed. Keep package status pending until the full completion gates above pass.

The source code does not define enough authority/identity to safely ship those writes yet. Before implementation, resolve these exact decisions/contracts:

1. **Writer boundary:** authorize the smallest change to `server/evidence/custody.py` (or explicitly revise `server/evidence/AGENTS.md`) so `evidence.evidence_item` can be written through the approved canon proposal without adding a competing `evidence` writer.
2. **Owner principal:** specify the authenticated claim/role that is the human owner, its stable value for `change_decision.decided_by`, and the rule preventing service credentials or `proposed_by` from standing in as owner approval. The `canon.change_decision` table alone does not authenticate its text field.
3. **Promotion field mapping:** define the source of `evidence.evidence_item.case_id` alongside `matter_id` and `court_case_id`, and the exact title/assertion/record mapping. The schema requires `case_id` and title (`:7031-7048`) while the disabled legacy writer maps `case_id` to `court_case_id` (`repository.py:838-848`); that legacy choice is not evidence of the canonical rule.
4. **Analysis origin binding:** define the supported Surreal record identity and the authoritative join/receipt that proves which `context.source_version` and retained original it represents. No current promotion route/executor implements this mapping.
5. **Idempotency authority:** choose the durable key location and uniqueness/locking contract for proposal creation, approval, evidence commit, and workflow dispatch/recovery. The current proposal schema has no idempotency key; the Knowledge-specific promotion ledger cannot safely stand in for all source promotions.
6. **Hash coverage:** define which source types require H2/H3 and their canonical record/chain constructions. Existing application code only supplies the SBV-specific H2/H3 path; arbitrary-format reuse would be invented custody semantics.
7. **Receipt and issuer authority:** identify the actual source-verification and human-authorization receipt producers, trusted issuer/key configuration, package status/read-back service, and delivery acknowledgment that will satisfy the package contract. Until these exist, expose pending/blocked status only.
