That supersedes the historical D-152 instruction to defer building promotion. It does not supply a real item, approve any promotion, or make the old producer safe to enable.

The canonical destination is `evidence.evidence_item`. The schema snapshot calls it the promotion target and says it is written only through a `canon.change_proposal` of kind `promote` after an owner ruling (`modules/Probata/probata/sql/bootstrap/schema_snapshot_20260907.sql:7031-7048,7089`). ## Required request and provenance shape

Use one promotion item per `canon.change_proposal`, even when the UI submits a batch. The request identifies an authoritative PostgreSQL `context.source_version`; the server resolves its `original_object_id` to `context.retained_object` and obtains the exact immutable locator/version itself. It accepts no bytes, filesystem paths, callback URLs, or caller-selected object-store URLs. In the current conversation projection contract, `surrealsink.Thread.SourceFiles[].SourceVersionID` and `surrealsink.Message.SourceVersionID` are explicit pins (`modules/engine/surrealsink/writes.go:22-43,51-65,117-139`). `Event.RecordIDs` and `Entity.Mentions` do not themselves establish a source-version join in the inspected producer path. Support those origin kinds only after a resolver proves their exact source mapping; until then, leave them unavailable and offer the pinned thread/message path. Surreal remains an analysis surface, never a second evidence writer.

The current retained-source read seam is `modules/engine/postgres/hash_repository.go::Repository.OpenOriginal`: it accepts an `original` reference, resolves it through `context.retained_object`, and opens inline bytes or the configured object opener (`:54-74`). The object-store path is `modules/engine/acquisition/objectstorage.go::ObjectStoreResolvers` / `NewObjectStoreResolver` (`:97-135`); `objectStorageVersion` rejects malformed, duplicate, empty, `null`, or oversized `versionId` values (`:221-237`). The current `SourceIntegrityStore.OpenSourceIntegrity` resolves a pinned workflow request and calls `OpenOriginal` (`modules/engine/postgres/source_integrity_store.go:111-117`). These are source-reading siblings, not a promotion workflow or custody hash writer. The source-integrity activity is a bounded byte assessment (`modules/engine/activities/source_integrity.go::AssessSourceIntegrity`, `:85-90`), and its store persists activity execution/receipt state; it does not establish H1/H2/H3.

Promotion retains the source-version ID, retained original-object ID, exact immutable object reference/version, independently re-read SHA-256 of the original, and the original/package fingerprint comparison required by D-154. For an analysis-origin item it also retains the Surreal origin reference and the resolved source-version mapping. The analysis reference is provenance, not authority to substitute another source. D-154 requires reopening the retained Intake Source Package and re-reading/rehashing the packaged original; an intake/context fingerprint cannot be relabeled as custody (`DECISION_LOG.md:345`). Do not add a category-wide filter for sources merely because they were routed through context or analyzed: D-154 says current context routing does not permanently determine later evidence eligibility. D-082 remains the cited boundary for the AI-chat conversation/model-produced text itself; it does not exclude an independent original source discussed by or analyzed from that chat (`DECISION_LOG.md:78,345`). The existing hash path may still report a source type unsupported until its own canonical hash contract is present.

## Proposal, ruling, and operation lifecycle

The schema supports `canon.change_proposal` kinds including `promote`, per-row `target_pk`, `patch`, `origin_surface`, `origin_ref`, `proposed_by`, `source_generation`, `tier`, and statuses `proposed`, `approved`, `rejected`, `stale_requeued`, `applied`, `failed` (`schema_snapshot_20260907.sql:7477-7493`). `canon.change_decision` records `proposal_id`, `decided_by`, `decision` (`approve`, `reject`, `requeue`), optional batch ID, note, and time (`:7461-7469`). The owner ruling is per item; a batch is presentation/orchestration only and cannot collapse approvals.

`canon.apply_proposal(proposal_id, decision_id)` performs a generation staleness check and says non-`correct` kinds are executed by their kind-specific worker (`schema_snapshot_20260907.sql:1088-1110,1115-1116`). However, the function does not check that `decision_id` belongs to this proposal or has decision `approve`; it also advances the canonical-table generation, inserts a `change_application`, and marks the proposal `applied` even for `promote` (`:1141-1157`). A promotion executor must not call it as though it were an owner-approval validator. The approved execution transaction must bind the proposal and its specific approved decision, reject wrong-proposal/non-approve/replay decisions, enforce `source_generation`, and commit the evidence item plus application receipt atomically (or add a specifically designed, durable kind-worker state that does not falsely call an uncommitted promotion `applied`).

Use a required client idempotency key and the existing durable `origin_ref` JSONB; no schema addition is needed for request deduplication. In the proposal transaction, take `pg_advisory_xact_lock(hashtextextended(key, 0))`, look up the key, and compare the canonical request digest plus stored request fields/source pin. An exact replay returns the same proposal; same key with changed payload returns conflict. The legacy Knowledge path supplies the concrete lock precedent (`repository.py:829-836`). Keep workflow dispatch recoverable by persisting the proposal/workflow identity before dispatch; never make client retry depend on an in-memory progress map.

Expose persistent status from durable proposal/application and workflow/receipt state. Pending approval, stale/requeued, running stage, failed stage, and package-blocked must remain visible. “Evidence committed” requires read-back of the exact `evidence.evidence_item` and its source/hash lineage. “Package complete” is a later status and must not be inferred from a proposal being approved/applied or a workflow returning success.

## Custody, hashing, and package completion

`server/evidence/AGENTS.md` names `server/evidence/custody.py` as the only writer of the `evidence` schema and `ingest_artifact()` as the H1/raw custody gate. Extend that sanctioned writer with a proposal-bound promotion operation; do not add a competing writer or enable the legacy `analysis.evidence_item` path. `ingest_artifact()` computes H1, deduplicates, writes the write-once blob and H1/source row; it does not generate H2/H3 (`custody.py:268-283`). `record_evidence_hash()` appends a supplied hash; `reconcile_sbv_import()` independently checks H1 and records the SBV-specific H2/H3 chain (`:541-643`). Reuse only an existing source-format hash contract; unsupported formats remain visibly pending/blocked, never get a borrowed hash construction. D-152 moved custody hashing to promotion time; D-154 requires exact original reread. Do not relabel a context fingerprint as custody.

The writer runs only after the verified per-item owner decision and uses source/version-bound idempotency so Temporal retries cannot create duplicate evidence items or custody chains. H1 is the original-byte hash; H2/H3 are emitted only where that selected source format already has a defined canonical record/chain contract. If that contract is absent, the item remains pending/blocked with its exact source provenance; it is not package-complete.

`server/contracts/legal_source_package.py::LegalSourceItem` requires exact evidence and assertion versions, source version/locator/content hash, a source-verification receipt ID, and a human-authorization receipt ID (`:92-122`). `assemble_package()` requires issuer/key ID and committed items (`:243-273`); its module header explicitly says no production issuer or route is wired while D-152 holds (`:1-5`). A package may be reported complete only after: (1) source reread and hash/version comparison succeeds; (2) the human authorization is recorded by the actual authorized principal; (3) the approved proposal and exact evidence row/hash lineage commit and read back; (4) assertion/version references and both required receipt IDs resolve; (5) the configured trusted issuer signs the package; and (6) package verification/current-status and the required delivery/read-back path succeed. No receipt or issuer identity may be fabricated to pass these gates.

## Recommended implementation choices

1. Add a strict request/status endpoint that records a proposal only; it must not start a non-existent executor or call `canon.apply_proposal` as an approval check. Read status from the durable proposal/application plus registered workflow/receipt state. Until a promotion worker is registered, return `execution_available=false` and keep the item visibly `proposed`/pending.
2. Resolve the canonical table at runtime by `(table_schema, table_name) = ('evidence','evidence_item')`; require exactly one registered row and its current generation. D-117 records that `evidence_item` is registered and explicit-review, and the schema says registration is an owner act (`DECISION_LOG.md:296`; snapshot `:7405-7423`). Make a deterministic proposed evidence-item UUID the `target_pk.id`; put the validated insert payload in `patch`; preserve exact source and analysis origin in `origin_ref`.
3. Use `case_id = court_case_id` as the default mapping, matching the existing case-management insert (`repository.py:838-848`). The snapshot gives `case_id` a not-null constraint and `(case_id, exhibit_number)` uniqueness but no separate case-registry FK; it enforces actual scope with `(court_case_id, matter_id) -> registry.court_case(id, matter_id)` and `matter_id -> registry.matter(id)` (`schema_snapshot_20260907.sql:7031-7040,22793-22821`).
4. Use the established Authentik identity pattern for the later ruling endpoint: verify RS256 signature, issuer, audience, expiry, `sub`, and configured group, then persist a stable `authentik:<sub>` actor. The sibling `modules/Legal-desktop/api/legal_workspace/api/auth.py::AuthentikTokenVerifier` and `require_human_review_actor` implement this; its default `advocatio-users` review group is not evidence-owner authority. Never treat Probata's shared bearer principal `platform-owner` or a Tailnet/device/service identity as the human decision actor (`modules/Probata/probata/server/api/main.py:65-107`).
5. In the single approval/commit transaction, require the exact `canon.change_decision` row for the proposal with `decision='approve'`, bind it to the verified actor, enforce the current generation, call the proposal-bound custody writer, and persist the `change_application` only with the evidence commit. This closes the currently unguarded `canon.apply_proposal` decision-ID gap (`schema_snapshot_20260907.sql:1088-1116,1141-1157`).
6. For AI-chat provenance, apply D-082 to the chat/model-produced text itself; do not extend it to independent original sources merely because they were discussed, context-routed, or analyzed. D-154 explicitly preserves later eligibility for sources that took a context route (`DECISION_LOG.md:78,345`). The Surreal-origin path promotes only the resolved original source version; the Surreal analysis object remains provenance.

## Remaining actual gates

- **Approval authority configuration:** no Propria evidence-owner Authentik group is configured in the current Probata API. The sibling Legal handler provides the verified-human mechanism, but its `advocatio-users` group is a legal review group, not an approved `canon.change_decision` authority. Until the correct existing group/claim is configured for this action, the decision endpoint must fail closed. This is the one remaining owner-authority fact; feature scope itself is settled.
- **Surreal read adapter:** the projection contract carries explicit pins for thread source files and messages, but no promotion-side reader uses them yet. Implement that bounded read/resolve adapter first. `conv_event.record_ids` and `conv_entity.mentions` lack a verified source-version join in the inspected producer path; keep those kinds unavailable until the join is traced and tested. Reject missing, multiple, or mismatched pins; no new identity or source registry is needed.
- **Package release configuration:** `assemble_package()` and `verify_package()` accept injected sign/verify callbacks; the Legal consumer is intentionally held and requires trusted issuer keys, a canonical producer snapshot, and atomic conditional inbox (`modules/Legal-desktop/api/legal_workspace/integrations/legal_source_package_v1.py:1-6,134-184`). Still required are the production issuer/key ID and protected signing-key binding, trusted verification-key binding, actual source-verification and human-authorization receipt producers, and the canonical snapshot/status/read-back plus delivery acknowledgment. Until those are configured and verified, package status remains pending/unavailable.
- **Executor implementation:** neither the current source-integrity Activity nor the legacy case-management route is a promotion executor. Build the separate source-reread/hash, supported-format H2/H3, canonical commit/read-back, and package stages as Temporal Activities; keep `canon.apply_proposal` behind the guarded transaction above. Existing `AssessSourceIntegrity` remains a byte assessment, not a custody hasher.

No request/status code is added in this revision. The direct route needs a new canonical proposal payload/reader, while the current API has no promotion-side Surreal resolver for the analysis path; a partial DTO or direct-only endpoint would not implement the requested two-origin request contract. Keep proposal creation separate from the later Authentik owner decision. The request, status, idempotency, actor, and payload choices above are concrete; the remaining human authorization and package-signing facts are implementation gates, not requests to reauthorize the feature.
