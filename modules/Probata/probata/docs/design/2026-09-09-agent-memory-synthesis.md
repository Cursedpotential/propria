## 1 · What the product is, in the docs' own words

- "SurrealDB Agent Memory is a memory and knowledge layer for AI agents. It is an application tier in front of SurrealDB, and every durable record lives in that database." Two binaries: `spectrond` (server: API, worker, scheduler, management, bootstrap) and `spectron` (client CLI). Install script at `download.surrealdb.com/spectron`, latest v0.2.1, Linux, macOS, and Windows archives.
- One graph, two streams: **authoritative** (`source.kind = "document"`, uploaded documents, higher default trust) and **experiential** (`source.kind = "turn"`, conversation and derived facts). Authority wins on conflict; the conflict is recorded, never silently overwritten.
- Retrieval is one read path over facts and passages: `/query` (hybrid BM25 + vector + graph, `k` default 10, cap 50), `/context` (ranked, formatted for prompts), `/chat`, `/reflect` (LLM synthesis, optional persist), `/forget` (expire, never delete), profiles, `state`, entity reads.
- Isolation is by **scope paths** (`org/acme/project/x/user/alice`), hierarchical visibility (a query at a broader path sees narrower ones), **principals** with attenuated keys over seven verbs (`memory:read|write|forget`, `scope:read|create|delete`, `grant:manage`), and **labels** (`key=value`) that narrow reads but never widen access.
- Time is tri-temporal; `observedAt` on upload stamps historical time; reads accept `asOf`; supersession chains keep old values auditable.
- MCP is served at `/mcp` on the same port as REST. The exposed tools: `remember`, `recall`, `context`, `reflect`, `forget`, `upload`, `inspect`. Harness adapters listed: LangChain, Vercel AI SDK, OpenAI Agents, n8n, Claude Code hook.
- Fixed costs of running it: the embedding model is "fixed per deployment" (`gemini-embedding-2`, 3072 dims, `SPECTRON_EMBEDDINGS_API_KEY`), and extraction, synthesis, and reflection stages call an LLM from `openai`, `anthropic`, or `google`, selectable per stage.

## 3 · The integration pages that matter, in one paragraph each

- **Embedded MCP (`surreal start` + `/mcp`, since 3.1):** the plain database's own MCP with generic tools (`query`, `run`, `select`, …), gated by `SURREAL_MCP_ALLOWED_HOSTS` (since 3.2.1). Relevant only if we keep our own SurrealQL docstore (option B below). Agent Memory has its own `/mcp` with the seven memory tools; the two are different servers.
- **CocoIndex:** SurrealDB's official incremental-indexing integration with table, relation, and vector targets. Needed only for option B's ingest; under option A the `spectron ingest ./docs` command is the ingest.
- **LangChain and LlamaIndex:** `langchain-surrealdb` is a plain vector store over the database; LlamaIndex has no adapter. Neither is the LangGraph read path D-143 ruled (Neo4j and Weaviate). For LangGraph agents that need memory, the Agent Memory **LangChain harness adapter** listed on the Embedded quickstart is the sanctioned door, not `langchain-surrealdb`.
- **Embeddings providers:** every example computes embeddings client-side; the database never calls a provider. Agent Memory sidesteps this entirely because `spectrond` owns embedding with its fixed Gemini model. NIM stays the embedder for `ccc` and for option B only.
- **n8n:** the official community node speaks HTTP to a SurrealDB instance (Root, Namespace, or Database credentials). For Agent Memory the n8n harness adapter or a plain HTTP Request node with a Bearer key is the path; the node itself is for option B. `casebible-n8n` sits on the same host as the memory server.
- **Agent rules and skills:** the eight official skills are installed in the home tree; the four `.mdc` rule files are a thinner Cursor-format alternative; the third-party `24601/surreal-skills` pack is unendorsed and frozen at 3.1.4. Keep the official eight; treat the third-party pack as reference only.
- **surrealctl:** a SurrealDB Cloud control-plane client; it never installs or runs `spectrond`. Irrelevant to self-hosting.

## 4 · What this changes about today's plan

The docstore we stood up today (local SurrealDB 3.2.0, bound schema, nine domain functions, the CocoIndex binding in progress) is a hand-built subset of what Agent Memory ships: documents upload and folder ingest with content addressing, hybrid retrieval, supersession, labels, scoped keys, MCP tools, and a CLI. The owner's standing rule is to minimize custom code. So the honest recommendation is:

**Option A (recommended): run Agent Memory twice.** One `spectrond` on the VPS in front of `surreal-case` for the shared experiential memory (D-157). One `spectrond` on the desktop, Windows build, in front of the local SurrealDB already running at `127.0.0.1:8462`, holding the documents as authoritative knowledge. Docs stay local (D-155) because the local server's data plane and object store are on this machine; only embeddings and extraction calls leave for the provider API, exactly as `ccc` already sends chunks to NIM. Two MCP servers, one plugin, progressive disclosure through skills, all off the shelf. The taxonomy (D-156) maps onto labels (`type=review`, `domain=proffer`, `status=active`) plus native supersession; the seven-folder mirror and generated INDEX remain ours, driven by the mapping table. Today's custom schema and functions become the fallback.

**Option B: keep the custom local docstore, use Agent Memory only for memory.** Everything built today stays live; the docs ingest goes through CocoIndex; the plugin wraps two different MCP dialects (SurrealQL `run` on one side, the seven memory tools on the other). More code to own, two vocabularies for agents to learn.

Costs that exist under either option and were not in play before D-157: a Gemini Developer API key for embeddings (free tier exists; volume is the 503-file docs tree plus session turns), and an LLM provider key for the extraction, synthesis, and reflection stages (per-stage model selection lets the cheap stages run on the cheapest model; `remember` accepts `infer: none|preview|triples|full` so bulk loads can skip extraction).

## 7 · CocoIndex: how the integration works and where it fits (owner question 07:01)

Read from SurrealDB's official CocoIndex page. The connector is a package extra: `pip install "cocoindex[surrealdb]"` (installed on the uv interpreter 07:03; `from cocoindex.connectors import surrealdb` now exposes `ConnectionFactory`, `TableTarget`, `RelationTarget`, `TableSchema`, `ColumnDef`, `mount_table_target`, `mount_relation_target`). The model is declarative and incremental: a pipeline declares what records and relations should exist; each run upserts changes, skips unchanged inputs (memoised steps, `COCOINDEX_DB` holds the change-tracking state), and removes records no longer declared, reconciling related tables in one atomic transaction. Targets are normal tables, relation tables with polymorphic `from`/`to` endpoints that become `RELATE` edges, and HNSW vector indexes whose metric or dimension change triggers recreation. Schema can be owned by the pipeline (`managed_by="system"`) or by us (`"user"`). Embeddings are computed client-side inside the pipeline, so NIM (D-158) plugs in as a function step; the docs' examples use local SentenceTransformer/FastEmbed models only to avoid API keys.

Where it fits here, by option:

- **Option A (Agent Memory holds the docs):** CocoIndex is not the docs ingest; `spectron ingest` is. CocoIndex still earns its place for **derived structure we own**: the taxonomy graph (document → supersedes → document, document → cites → document, document → decides → ADR, todo → closes → decision) declared from the mapping table and kept in sync on every run, written to the local SurrealDB as relation tables. That graph is what the mirror generator and INDEX read, and it is exactly the incremental-reconciliation shape CocoIndex is built for. It is also the natural home for the code index that `ccc` already maintains, if that ever needs to land in SurrealDB.
- **Option B (custom docstore):** CocoIndex is the whole ingest: source = `docs/**/*.md`, transform = heading-aware chunking plus NIM embeddings, targets = `document` and `chunk` tables (`managed_by="user"`, our schema) plus the `supersedes` relation from the mapping table. The five-file dry run in progress is this path.
- **Either way, the evidence corpus later:** the flagship example (`conversation_to_knowledge`) is transcripts → statements → people, technologies, organisations → mention edges, with LLM extraction and entity resolution. That is the proffer-to-consignatio shape (messages → claims → people → mention edges), and CocoIndex's atomic reconciliation is how a re-ingest replaces a corrupt run without orphaning edges. Flagged with the historical-data cookbook as the next design, not started.

Can it make Agent Memory "better"? Yes in one specific way: Agent Memory ingests documents and extracts entities on its own, but it does not maintain our external structure (taxonomy edges, decision closures, mapping-table truth). CocoIndex keeping that structure reconciled in SurrealDB, and Agent Memory answering from the documents, is a clean split: CocoIndex owns declared truth we control; Agent Memory owns extracted memory and retrieval.
